## B1. The bootstrap mirror is justified, but needs an explicit upgrade contract

At `src/bot.rs:1155-1187`, `join_azalea` replaces two azalea join calls with a copy of app construction, plugin registration, runner startup, connect options, and event-channel wiring. This is a new maintenance obligation, not evidence of an incorrect bootstrap. Compared with pinned azalea `azalea/src/client_impl/mod.rs:84-117` and `:183-204`, the default plugin groups, runner creation and immediate startup, resolve-before-join behavior, event sender, and proxy application to both the server and session server match. Dropping the app-exit receiver also matches `StartClientOpts::new`, which returns only tuple element zero. I would not report an exit-receiver leak or proxy regression.

The hook is necessary. `src/interact.rs:293-304` explains that a pending start materializes under the same ECS lock as mining, so an outside task cannot reliably stop it before creative instant-break. `DigAbortPlugin` registers reconciliation before `MiningSystems` at `:383-391`. Replacing this with a later polling task, inserting systems after runner startup, or removing default plugin groups would be unsafe. Pinned `ClientBuilder` has plugin registration, but its long-running handler-based start contract differs from this crate's returned `Client` and raw receiver. Switching would add lifecycle plumbing rather than delete it.

What is missing is a precise source-and-test contract. Comments at `src/bot.rs:1041-1045` and `:1149-1154` repeat the rationale but omit the pinned revision and upstream source path that must be checked during an upgrade. Reconciliation tests at `src/interact.rs:1472`, `:1502`, and nearby call `reconcile_aborted_dig` directly. They cannot catch deleting `app.add_plugins(DigAbortPlugin)` or ordering it after mining. Keep the mirror, document the upstream location and plugin/runner/proxy obligations once, and add one network-free schedule-level test using the same app-construction function as production. Enqueue a pending start for an aborted generation, drive the real Update/GameTick sequence, and assert that mining cannot act on it. This checks integration rather than matching a magic source string. This is a medium-priority maintenance/test gap introduced by the phase; no runtime defect is claimed.

The right home is a private connection module under `bot`, not `interact.rs`. Networking, LocalSet, proxy policy, and startup belong to the connection owner; dig owns the plugin. If `bot` is decomposed, put `join_azalea` with the thread/runtime connection code in `bot/connection.rs`. Moving only the 33-line function into an otherwise empty global bootstrap module buys little. Do not add a public plugin framework for one hook.

## B2. One shared-state constructor would delete repeated domain wiring

`src/bot.rs:56-112` stores reason slots and six domain state handles directly on each `Bot`. `connect_azalea` allocates them at `:1086-1102`, enumerates cloned handles into `BridgeDeps` at `:1114-1125`, and lists originals in the returned `Bot` at `:1129-1144`. `Bot::new` has a second allocation list at `:1202-1222`. The bridge repeats the domain list at `src/bridge.rs:30-64` and destructures it at `:83-95`. A new tracker touches both constructors, both dependency/field descriptions, the destructure, and the call site. The `BridgeDeps` comment says the bag exists to stay below Clippy's argument limit; duplicated ownership descriptions are the actual problem.

Use one `Arc<BotShared>` with the existing separate domain locks and reason slots, constructed once by `BotShared::new(events, domain_defaults)`. Both `Bot` and the bridge hold it. Both construction paths use that constructor, while the scaffold's exceptional lifecycle behavior stays explicit. `BridgeDeps` then contains only connection policy or becomes `BridgeOptions`; it need not clone and relist every domain. Keep `Arc<Mutex<WindowTracker>>` inside the object so the window handle's existing weak tracker link still works. Keep domain locks separate, not one global mutex. This deletes initialization and wiring duplication without a generic state registry.

Do not put `_alive`, `_shutdown_tx`, or the bootstrap receiver into an object owned by the bridge. Last external `Bot` drop must still close the alive channel; bridge exit must still drop the shutdown sender. This is a medium-priority pre-existing simplification, not a regression caused by the eight-line production bridge change.

## B3. Delete the private frozen-signature exception for view distance

`src/bot.rs:776-783` stores `view_distance` separately from optional `ClientInformation`, which already contains that field. The setter at `:889-891` writes the separate value. The bridge carries it as a positional parameter at `src/bridge.rs:73-80`, then the merge at `:419-434` reconstructs client information and gives the separate field precedence. The comment at `:414-417` says the signature is frozen. Searching all source files finds exactly one `bridge::spawn` caller, `src/bot.rs:1107`, and `bridge` is private in `src/lib.rs:23`. No public compatibility boundary justifies two representations of one setting.

Make `BotBuilder::view_distance` write `self.client_information_mut().view_distance = value.into().chunks()`. Remove the separate field/default, bridge parameter, and `init_client_information`. Event::Init sends the optional completed struct directly. Unset options still send nothing; either setter order preserves view distance because the existing getter initializes the struct only once. This deletes a precedence branch and its special-case tests rather than moving them to another helper. Keep behavior tests for unset settings and both setter orders. This is a medium-priority missed simplification already present before the phase; the new kick handling does not worsen it.

## B4. Give each typed window one state record

`src/window_types.rs:149-164` models one protocol window across five parallel keyed collections: kinds, data, offers, selected trade, and readiness. `clear_window` at `:172-177` removes the same id five times, while login/respawn at `:258-264` clears all five separately. Accessors repeat id lookups through different maps, for example `:447-462`, `:616-638`, and `:972-989`. Every new per-window field creates another synchronized table and cleanup obligation.

Use `HashMap<i32, WindowData>` with `kind: Option<MenuKind>`, a property map, `offers: Option<Vec<VillagerTrade>>`, `selected_trade: Option<usize>`, and the readiness latch. Close removes one record; login/respawn clears one map; fresh OpenScreen replaces one record. Data and offer packets use `entry(id).or_default()` so pre-open packets retain the current behavior. Optional offers matter: `open_villager` at `:1120-1137` distinguishes an arrived offer packet, possibly empty, from no packet. An empty-vector default would break that contract. Preserve an absent kind for data arriving before OpenScreen. This is a medium-priority pre-existing state-model issue, with a concrete deletion of repeated cleanup logic. It does not justify putting typed-window policy in the bridge.

## What is fine in the bridge and what should not be generalized

`src/bridge.rs:107-204` is long orchestration, but the order is deliberate. Movement, pathfinder, entity, window, typed-window, recipe, and world observers update state before their derived batches are emitted. Comments at `:147-164` explain why ECS patches and packet-derived updates run in one ordered consumer rather than broadcast subscribers. The shutdown channel at `:226-233` exists because tick senders remain alive through clients held by driver tasks. Keep these operations direct and sequential. Parallel observers or background subscribers would restore packet-loss, order, or shutdown problems documented in the code.

The new kick discriminator at `src/bridge.rs:325-332` reuses the established login flag. It is better than adding another independent login latch or nullable mode. It adds no significant spaghetti; tests cover login-phase and in-game kicks. This 501-line production module does not need decomposition just to lower its 1,051-line physical total. If it grows further, chat packet handling at `:475-500` has an obvious canonical home in `chat`. A dynamic event middleware framework or trait-object observer list would make the explicit order harder to audit.

State accessors in `tool.rs:77-90`, `pvp.rs:148-165`, `auto_eat.rs:201-221`, `collect.rs:142-160`, and `pathfinder.rs:697-711` repeat short ECS read or insert-default/write patterns. They protect different state types and initialization/disappearance choices. Leave the direct helpers unless they gain truly shared policy. A generic plugin-state registry would save few lines and introduce type bounds and another layer. The constructor wiring in B2 is the better target.

Mining formulas are already canonical. `src/interact.rs:871-895`, `src/tool.rs:121-138`, and `src/pathfinder.rs:1122-1162` all call azalea's `get_mine_progress`, not independently drifting mining algorithms. Their contracts differ. Dig time scores the held item and handles creative instant-break. Tool selection can consider bare hands when a slot is free and can require correct harvesting. Pathfinder's tool scan excludes empty stacks and rejects zero progress. A policy-rich common selection helper would hide those differences. A common mining-context snapshot could help if more scoring code appears, but these formula calls alone offer no dramatic deletion.

Event sending is similarly simple. `Bot::emit_event` at `src/bot.rs:1376-1378` is the normal bot-side helper. The bridge and Window::close use raw senders because they do not own an external live Bot; requiring one could alter lifetimes. They do not need an EventEmitter abstraction. Chaining the bridge's six simple send loops is an optional local shortening, not a major review finding.

One narrow wait consolidation is worthwhile during the window split. `inventory::wait_for_slot_update` at `src/inventory.rs:864-880` and `window_types::wait_for_slot_updates` at `src/window_types.rs:1448-1468` have the same bounded, best-effort slot-update contract. The first can call the second with a one-element slice after both live in a shared private window-event module. Preserve the single consumer and outstanding-slot set. The comment at `window_types.rs:1444-1446` correctly warns that sequential per-slot waits consume each other's events. Do not replace every wait loop with one generic function: chat's await_message is unbounded, inventory open waits return different errors, chunk waits recheck state after lag, and dig waits depend on ticks, generations, and shutdown. Shared code must not silently unify their terminal conditions or failure information.

## Decomposition that improves the current crate

The flat public module layout is a reasonable API map. It should not force every implementation of a domain into one file. Preserve existing module paths and root re-exports by turning selected files into directory modules with private children. Multiple child files can contain impl Bot blocks without adding runtime abstractions. Split by ownership and algorithm, not arbitrary line counts. Move behavior tests with their owner, not merely to make source totals look smaller.

`src/interact.rs` is the most urgent phase-related decomposition. It has 1,403 production lines, 317 more lines before the test attribute than the baseline. The new cancellation reconciliation and old promise wait/retirement machinery occupy the same file as placement geometry, entity placement acknowledgments, raycasting, and block activation. Put the dig state, plugin, reconciliation, abort/retire/settle, and dig promise in `interact/dig.rs`; keep their generation and lock boundaries together. Put placement options, geometry, entity/block placement and acknowledgments in `interact/place.rs`. Keep shared raycast/use-item-on mechanics in one small private child only if both need them. Re-export public option enums through `interact/mod.rs`. Do not split the abort plugin away from the generation model it protects. The file-size regression is real even though the 1,000-line boundary had already been crossed before this phase.

`src/bot.rs` has 1,388 production lines, but `BotEvent` alone runs from `:120` through `:742`. Move that 623-line event contract and its necessary imports into `bot/event.rs`, re-export it from `bot`, and keep `pub use bot::BotEvent` unchanged. This is a justified single enum: events are one broadcast protocol, so replacing it with nested event envelopes would cause downstream match churn without simplifying behavior. Move Auth, builder policy, thread/runtime startup and join_azalea into `bot/connection.rs`. The remaining handle/lifetime/event-subscription methods then fit comfortably in bot/mod.rs. Combine this with B2 rather than copying another initialization list into the new file.

`src/pathfinder.rs` has 1,885 production lines. It is a facade over azalea, but it is not a thin facade whose bulk must stay together. The Goal adapters occupy roughly `:162-492`; movement policy and its azalea adapter occupy `:504-643`; public control and promise behavior run through `:1247`; drivers are at `:1305-1484`; snapshot/event reduction runs from `:1488-1885`. Extract `goals.rs`, `movements.rs`, and a private `tracking.rs` containing PathTracker, PathSnapshot, snapshot, and bridge_events. Keep generations, facade writes and issue/stop together; put watcher loops with that owner unless extracting them reduces cross-private access. The long comments document real Update/GameTick and cumulative-timeout issues, not incidental clutter to delete. A decomposition should make those algorithms independently reviewable and preserve every current ordering/generation test. Do not replace them with a generic task/state-machine engine just because the adapter is large.

`src/window_types.rs` has 1,469 production lines and no compelling reason to combine furnace, enchantment table, anvil, villager trading, book editing and command blocks. Split furnace methods and ratios at `:370-547`, enchantment at `:556-720`, anvil at `:729-948`, and villager offer decode/trade logic at `:280-361`, `:957-996`, and `:1103-1292` into private children. Book input/edit/ack logic and command-block protocol logic can share a small ancillary file initially rather than forcing one tiny file per type. Keep server-pushed WindowData and the bounded event helpers in private shared children. Apply B4 here so the split removes duplicated cleanup concepts rather than scattering five tables over files.

`src/windows.rs` has 1,242 production lines. The `Item` snapshot at `:73-196`, `Window` handle and slot/query/close API at `:200-603`, and bridge-side `WindowTracker` with slot patches at `:612-1242` are clear seams. Put Item in `windows/item.rs`, the packet reducer and tracker in `windows/tracker.rs`, and the handle in windows/mod.rs. Preserve the current Weak tracker link and copyInventory-before-close ordering at `:493-533`. The phase's content/slot patches belong with the tracker, not in a generic bridge module. This split also gives the narrow slot-wait helper a canonical window-owned location.

`src/entity.rs` has 1,300 production lines. Move packet-derived EntityTracker and its decode helpers at `:64-590` into `entity/tracker.rs`; it already has a single observe_event entry. Keep EntityExt and query/player methods together. Explosion calculations at `:1109-1241` are a cohesive algorithm that can live in `entity/damage.rs`; profile skin decoding can remain with Player rather than getting its own file only to meet a count. These are separate ownership seams, unlike an arbitrary split at line 1,000.

`src/world.rs` has 1,210 production lines. Block/WorldRef and spatial queries belong together, including the raycast and find_blocks algorithms. The Time/Game/WorldState model at `:395-565` and packet/LidCounts reducer at `:957-1210` can form `world/tracker.rs`, leaving world reads and geometry in world/mod.rs. Sign serialization can stay with the small world Bot API; it does not need another top-level module. Preserve the bounded old-block-update cache because the comment at `:462-474` explains why reading the already-applied ECS cannot recover the prior state.

`src/inventory.rs` has 1,079 production lines. This is only modestly over the limit, but it combines equip/use/consume/openers with a second independently testable cursor-transfer algorithm. Extract TransferOpts, click adaptation, put_selected, toss_leftover and transfer at `:164-235` and `:831-1079` into a private `inventory/transfer.rs`, keeping existing public paths through re-exports. Do this when touching transfer behavior or the shared window waits, rather than as a high-risk all-at-once inventory rewrite. The remaining inventory API is cohesive enough to keep in one file.

`src/misc.rs` has 1,036 production lines and a real ownership problem beyond size. ScoreboardState is effectively in MiscState at `:41-52`, with scoreboard packet dispatch at `:192-194`, while scoreboard's public readers and reducer live in `src/scoreboard.rs:262-318` and depend back on MiscState. Meanwhile creative in-flight slot guards and fishing cancellation live in the same component at misc.rs:65-69. Move scoreboard maps/reset/reducer ownership into scoreboard's own state. Move Creative and CreativeSlotGuard at misc.rs:855-1036 into a private misc/creative.rs, keeping their resource and cancellation behavior together; settings can remain in misc/mod.rs with resource-pack operations. Avoid a separate module for every five-line operation. This is pre-existing boundary drift, not a reason to reject the new RAII slot guard or the independent-slot join_all flow at `:969-977`; both address real cancellation semantics.

`src/craft.rs` has 975 production lines, so it has not crossed the threshold and was not changed in this phase. Roughly `:497-711` is an explicit item-tag dispatch table, not arbitrary branching in the crafting orchestration. The Recipe model, recipe-book conversion, and grid execution are coherent and already separated by sections. I would leave it alone in this phase. If new recipe formats push it beyond the limit, extract RecipeBook plus protocol display decoding at `:266-711` into `craft/book.rs`, preserving the direct execution flow. Do not generate a registry framework simply to replace an exhaustive data mapping.

The other physical files above 1,000 lines do not necessarily need splitting. `auto_eat.rs` is 606 production lines, `chat.rs` 723, and `collect.rs` 809. Their remaining lines are tests. Keep those cohesive implementations unless a new ownership problem appears. Layout work should begin with interact, bot's event/connection contract, typed windows, and pathfinder, not a repo-wide cosmetic shuffle.

## Cargo dependency expression

`Cargo.toml:94-121` is a reasonable expression of the mandatory azalea pin. All 21 patch entries use exactly `ddef37118448b639ff56b86ae339e8913cb4ed11`; parsing Cargo.lock confirms exactly 21 azalea packages, all with that one git source/revision, and no second registry copy of any of them. The rationale at `:94-99` identifies the wire-format defect and fixed commit. Cargo does not provide a variable that can be interpolated into all patch values, so a generator, custom preprocessor or workspace conversion just to avoid the repeated literal would be worse. Keep the explicit table and the lockfile. Add a short comment that the table deliberately covers the whole same-source azalea workspace to prevent a partial registry/git graph; that makes the long list's purpose clear. Do not reduce it to an azalea-protocol-only patch or loosen the revision.

There is small, phase-exposed dependency debt at `Cargo.toml:15-17` and `:26-29`. The direct azalea-chat comment says the component/style types are not re-exported by azalea::chat. At the pinned revision, `azalea/src/lib.rs:50` says `pub use azalea_chat as chat`; the phase has correctly moved ChatPacket uses to azalea::client_chat. The old comment is therefore now false, and all direct azalea_chat uses in chat.rs and scoreboard.rs can use azalea::chat instead. That lets the crate remove the direct azalea-chat dependency, without removing its patch entry because it remains transitive. Also remove the duplicate azalea dev-dependency: integration tests already see normal dependencies, and this entry adds no test-only features. Both are low-severity hygiene issues, not dependency-graph breakage or reasons to change the approved pin. The stale MiscState comment at `src/misc.rs:53-55` claiming uuid is absent is another example of comments describing an obsolete dependency set; remove that assertion rather than preserving an artificial type limitation.
